Eval Harness Framework: the plan

The single page for this project: what we're building, how it's wired, what we support, and the tiers of work. Last updated 17 Oct 2026. It's updated whenever a tier moves; the change log is at the bottom. Repo: dataagentsai/eval-harness-framework.

In one line: one framework that checks AI agents (quality, security, cost and the business's own rules), using the best check from any provider, giving one result you can trust, and plugging into the tools a team already uses.

Why it's needed: every agent project rebuilds the same things: read traces, run some checks, call a guardrail service, apply rules, show results. Each eval and guardrail tool has its own data shapes, so using two tools together means writing glue every time. This framework writes that glue once.

What it is not: it isn't a database, a UI, a dashboard product or a semantic layer. It feeds the ones a team already has (LangSmith, Langfuse, App Insights, Grafana) and ships ready-made content for them.

How it relates to the Agent Assurance Layer: the Assurance Layer is the spec (what must be true about an agent). This framework is the implementation (the engine that checks it).

Keep it simple: version 1

This page is a map of everything. Version 1 is a small slice of it, built to answer one question: does a team find real problems in its own data that it didn't know about? (Decision D13.)

Six rules:

  1. One user, one job first.
  2. Deterministic first: plain-code checks before judge models.
  3. Users learn three things: the rule, where it runs, what happens.
  4. One adapter per role per stack.
  5. Every addition is asked for by a real team, or replaces something.
  6. A measured complexity budget: one install command, the team's YAML on one screen, first report within an hour.

After version 1: version 2 adds inline blocking and alerts; version 3 adds existing tools (LangSmith, Langfuse, Prometheus) and the rest of the loop; version 4 adds conversation and the standards work.

Architecture

Data comes in from where the agent already writes it, flows through one engine, and goes out to the tools the team already uses. During processing, the engine calls outside services for the checks themselves.

The ports

A port is an interface. The engine only knows the port; each tool sits behind an adapter that implements it, chosen by name in YAML.

Who writes the rules

Writing a rule and placing it are separate jobs. A rule is written once; YAML decides where it runs and what a failure does. Rules are YAML in the repo, reviewed like code, and every result records the rule's version.

WhoWritesExample
Us (framework)Built-in packs: ops metrics, the 36 cost rules, security checks, the five domain patterns, the adaptersLLM-15 loops, PII check, requires_before
Agent or domain teamDomain patterns filled in with their tool names and limits"cancel_order needs get_order", "refund ≤ ₹5,000"
Risk, compliance or ops ownerPlacement and consequence: which position, block or alert, sampling, thresholds"refund over limit: block at pre_tool, count online"
The Assurance spec (later)Rules generated from obligations by the compilerEach obligation becomes one or more rules

Inline: the five moments

These positions already exist in agent_harness.policy.Position. What a block does depends on the moment. Rule of thumb: inline only takes fast checks (plain code or a small classifier within a time budget). Large judge models go online.

PositionMomentWhat a block doesTypical checks
pre_modelBefore the request goes to the modelEnds the turn with a refusal, so nothing is paid forInjection in the user message or retrieved documents, context over limit, missing output limit (LLM-16), budget cap
post_modelThe model answered; nothing has acted on it yetEnds the turnUnparseable output (LLM-27), output schema, reasoning budget used
pre_toolThe model chose a tool and arguments; it hasn't runReturns an error to the model, which may choose againAllow-list, refund limit, "cancel needs get_order", loops (LLM-15)
post_toolThe tool's result, before it enters the contextReplaces the result; the action itself already happenedInjection hidden in tool output, personal data from a backend system
replyWhat the customer is about to read, on every routeA safe reply insteadPII, unbacked promises, facts matching tool results

"While a tool runs": the tool is outside us, so we can only check just before (pre_tool) and just after (post_tool). Checking a reply while it streams isn't supported yet (open decision D8).

  • The converter isn't a separate hop. It's the normalise step, inside the eval worker in both cases.

Built once, used by every team

  • Jobs are written against ports, not tools. A job calls TraceSource and ResultSink and never knows which tool is underneath.
  • Each tool needs one small adapter with five methods: read_traces, write_score, add_to_review, read_labels, add_to_dataset. A tool without a feature declares it, and that step is skipped for that tool. Work grows as jobs plus tools, not jobs times tools.
  • One shared eval worker per environment, run by a platform team, serving all agents. Each agent team only adds YAML. Onboarding a new agent is a config change.

Keeping the work under control

  • Support a short list properly: Phoenix or Langfuse (open stack), App Insights (Azure), LangSmith when a client brings it. Everything else is on request.
  • Never build what the tool has: no review UI, no dataset UI, no alerting engine.
  • Steps 1–6 first (the core loop), then 7–11 one at a time.

Turning checks on and off

# agent's evaluators.yaml
preset: customer-support-azure
rules:
  presidio_pii:        {mode: block}                 # off | shadow | alert | block
  ragas_faithfulness:  {mode: off}
  refund_limit:        {mode: block, params: {max: 5000}}
  llm_16_output_limit: {mode: shadow, positions: [pre_model]}
  1. Preset: our defaults.
  2. Org policy (risk owner): rules marked locked: true, such as PII and refund limits. The agent team can't turn them off; at most they can request shadow mode, with approval.
  3. Agent YAML: everything not locked is the team's choice.

A runtime switch moves a misbehaving rule to shadow without a redeploy (through a config store such as Azure App Configuration). Every switch records who, when and why. Without locked rules, the easiest way to "adopt" would be switching everything off.

dbt is the closest model for what we're building, and it points to a possible reuse.

Where it breaks, which is also what makes us more than "dbt for evals":

  • Inline. dbt only runs in batches over stored data. We also run inside the request, in milliseconds, and can block.
  • Judgement. A dbt test is exact. Many of our checks are a judge model's opinion, so they need precision measurement, human labels and calibration.
  • Many shapes. dbt only speaks SQL tables. We map messages, tool calls, traces and scores across many tools.

Lessons: the basic test must be as easy to write as not_null; run where the data is; it creates a role (our rule writers, the way dbt created the analytics engineer); community packages beat core features.

Possible reuse (decision D10): the batch cost rules are SQL over call records, which is exactly what dbt runs. Shipping them as a dbt package would give every warehouse dbt supports for free (dbt-duckdb locally; Databricks, Snowflake, ClickHouse, BigQuery for clients), with Elementary for alerts. Limits: no dbt adapter for Log Analytics (KQL), and it adds dbt as a dependency.

Lessons from OpenTelemetry

OTel won by being the thing every vendor plugs into. That's the position we want for eval.

#What OTel doesWhat we take from it
1A tiny API, separate from the SDK; the API does nothing until an SDK is installedOur agent-side hook package is the “API”: tiny, no vendor dependencies, does nothing until configured. Adapters and judges are the “SDK”, in the eval worker.
2Never break the appWatching fails open by default; blocking rules state their choice explicitly (fail-closed for PII, refund limits).
3Semantic conventions: agree on names, not codeThe biggest lesson. Publish our result format as conventions (eval.rule.id, eval.verdict, eval.score, eval.finding.kind), not a private class, so any tool can read results without our code. OTel's gen_ai.evaluation.result exists: adopt it and extend only the gaps.
4The Collector pipeline: receivers, processors, exporters, wired in YAMLSame shape for us: sources, checks and decide, sinks, wired in YAML. Borrow the vocabulary.
5Core versus contrib, each contrib component with named ownersA small core we maintain; adapters in contrib, each with an owner (a vendor or client can own theirs).
6Stability levels per componentEach adapter labelled alpha, beta, stable or deprecated.
7Context propagation (trace id across services)Inline results ride on the trace id, so online knows what was judged; session id and agent version travel the same way.
8Tail sampling: decide after seeing the whole traceJudge interesting sessions first: errors, blocks, escalations, high cost, new prompt versions; then a small random baseline.
9Resource attributes (service, environment, version) on everythingAgent name, version, environment and prompt version on every result; LLM-35 and LLM-36 depend on it.
10Separate signals: traces, metrics, logsResults as events on the trace, counts as metrics, findings as their own records.
11Neutral governance made vendors contributeApache-2.0, open conventions and contrib ownership, so providers can write adapters.

Not to copy: OTel's complexity, its most common complaint. Hence presets: OTel's design underneath, simple on the surface. Warning: the GenAI conventions are still experimental; we pin a version and the trace adapter translates.

Why there's no open standard for eval, and what we do

LayerStandardCovers our need?
Traces (the input)OTel GenAI conventions (experimental); OpenInferencePartly. It defines gen_ai.evaluation.result (name, score value, score label, explanation, response id), status Development; no scale, threshold, findings or rule identity. The conventions moved to open-telemetry/semantic-conventions-genai in May 2026 and have no release yet.
Model benchmarksMLCommons AILuminate, Stanford HELM, Inspect logsNo. These score models, not your agent in production.
Management and processNIST AI RMF, ISO/IEC 42001, EU AI ActNo. They say you must evaluate, not in what format.
Application eval results and rulesNothingThe gap: what a check returned, on what scale, by which judge, under which rule.

Why nobody has standardised it:

  1. Eval is where vendors make money. A common format makes switching easy. OTel became a standard once tracing vendors moved their differentiation up into analysis; eval vendors haven't yet.
  2. The field changes every few months (RAG answers, then tool-using agents, then multi-agent). Standardise too early and you freeze the wrong thing.
  3. Scores aren't comparable without context. Azure's 3 out of 5 and Ragas's 0.6 mean nothing side by side without the scale, threshold, judge model and prompt.
  4. Judges aren't repeatable, so a result must record the judge's model and prompt version.
  5. Nobody owns it. OTel had CNCF; application eval sits between ML researchers and software engineers.
  6. The input isn't stable yet: the trace conventions are still experimental.

What can be standardised now: not the algorithms, but the envelope around a result, which the spike produced: rule id and version, verdict, score with raw value, scale and threshold, judge model and prompt version, cost, latency, findings with positions, what was dropped, position, finding lifecycle. Declarative patterns such as requires_before too.

What we do: don't invent a sixteenth standard. (1) Adopt OTel's GenAI evaluation fields if they exist. (2) Propose the gaps upstream to OpenTelemetry, with the spike as evidence. (3) Only if that's blocked, write it as a spec in the Clean AI Engineering family beside AAC and AHC. See decision D12.

The adoption path

  1. Day 1, no code change: read their existing traces, run the packs over the last 30 days, deliver the report. Results appear in the tool they already use.
  2. Weeks 1–4, shadow mode: online checks run, nothing blocks, humans label a sample to measure each rule's precision.
  3. Then, rule by rule: precise rules move up to alerts; only the highest-stakes (refund limit, PII) move up to blocking inline.

How we'll know

  • Time to first useful finding under one day.
  • False-alarm rate per rule, from human labels.
  • Share of rules with an owner.
  • Inline latency added; eval cost as a share of agent cost.
  • Kill signal: a pilot team switches it off after four weeks of shadow mode. Then the problem is the product, not the team.

Content packs

A pack is configuration, not code: a set of checks or rules, ready to switch on in YAML.

Quality

Groundedness, faithfulness, relevance, tool correctness, task completion. Taken from the eval SDKs.

Security

PII and secrets in output, prompt injection and jailbreak on input, harmful content, tool allow-list and argument limits, cross-customer data. From the guardrail tools plus our own tool-call checks.

Cost

LLM-01 to LLM-36. About 8 can run inline as guardrails, 9 per trace, and the rest over many calls. Six are built today.

Domain patterns

requires_before, argument_limit, claim_needs_action, decision_vs_should, consistency, filled in with the domain's tool names and limits.

Questions it must answer

Any domain (built in)

  • How often did each tool fail, and was it the tool or a malformed call?
  • How often did the context cross its limit or get truncated?
  • How often did a turn hit the step cap, or loop on the same tool?
  • How did turns end: answered, gave up, escalated, crashed?
  • Cost per session, per resolved case, per agent version; eval cost as a share of agent cost.
  • Response time per turn and per tool.
  • Blocks per check and position; blocks followed by the user rephrasing.
  • Did anything shift after a release, prompt change or model change?
  • How often were checks skipped or errored? How often do judges disagree?

Domain-specific (patterns + YAML)

  • How many cancels happened with no order lookup before them? (requires_before)
  • How many times was the refund limit crossed? (argument_limit)
  • How many times did the agent promise something it didn't do? (claim_needs_action)
  • Did we over-escalate or under-escalate? (decision_vs_should)
  • Did the reply's facts match the tool results? (consistency)

Words used here

PortAn interface the engine depends on, such as "something that runs a check".
AdapterOne tool's implementation of a port, such as "Presidio as a check".
BindingThe YAML choice of which adapter fills each port, per stack.
Upstream / downstreamTools we read data from / tools we write results to.
HostA tool that calls our checks while it runs, such as an agent framework or a gateway.
CalledA service we call during a check, such as Azure Content Safety or a judge model.
PositionThe moment a check runs. Inline: pre_model, post_model, pre_tool, post_tool, reply. After the fact: online, release, scheduled.
Tap / pullTwo ways online checks get traces: a copy sent by the OTel Collector, or reading them from where they already land.
MCP serverA small service that gives an AI assistant tools; here, tools to query eval metrics.
GrainHow much data a rule looks at: one call, one session, or many calls over days.
JudgeA model that grades another model's output.
FindingOne thing a check found, with where it is and how bad it is. Over time a finding is new, ongoing, resolved or regressed.
Content packReady-made checks, rules, dashboards or metric definitions, switched on in YAML.
Spec / implementationThe Assurance Layer says what must be true; this framework checks it.
